# Transaction Ledger API — API Documentation

## 1. Overview

The Transaction Ledger API is a RESTful backend for managing accounts, recording credit and debit transactions, and transferring money between accounts.

### Base URL

```text
http://localhost:3000
```

### Content Type

Requests containing a JSON body should use:

```http
Content-Type: application/json
```

### Response Format

Successful responses generally use the following structure:

```json
{
  "success": true,
  "data": {}
}
```

Error responses depend on the error-handling middleware and may contain a `message` or `error` field.

## 2. Health Check

### Check API health

Checks whether the backend health endpoint is responding.

Example:

```http
GET /health
```

The exact response body depends on the implementation in the server.

## 3. Account APIs

### 3.1 Create an account

**Endpoint:** `POST /api/accounts`

Creates an account with an initial balance of zero.

Request body:

```json
{
  "name": "Savings Account"
}
```

Example success response:

```json
{
  "success": true,
  "data": {
    "id": "ACCOUNT_UUID",
    "name": "Savings Account",
    "balance": "0.00"
  }
}
```

The account ID is generated by the backend. Additional response fields may be included.

Validation:
- Account name is required.
- Empty or whitespace-only names should be rejected.

### 3.2 List accounts

**Endpoint:** `GET /api/accounts`

Returns a paginated list of accounts.

Query parameters:

| Parameter | Description | Example |
|---|---|---|
| `page` | Page number | `1` |
| `limit` | Number of records per page | `10` |

Example:

```http
GET /api/accounts?page=1&limit=10
```

Example response structure:

```json
{
  "success": true,
  "data": {
    "accounts": [],
    "pagination": {
      "page": 1,
      "limit": 10,
      "totalRecords": 100,
      "totalPages": 10
    }
  }
}
```

The values above are illustrative; actual totals depend on the database.

### 3.3 Retrieve all accounts

**Endpoint:** `GET /api/accounts/all`

Returns all accounts without pagination. This endpoint is used to populate the source and destination account dropdowns on the transfer form.

Example:

```http
GET /api/accounts/all
```

Response structure:

```json
{
  "success": true,
  "data": [
    {
      "id": "ACCOUNT_UUID",
      "name": "Savings Account",
      "balance": "0.00"
    }
  ]
}
```

The response may include additional account fields.

### 3.4 Retrieve account summary

**Endpoint:** `GET /api/accounts/summary`

Returns aggregate account information for the dashboard.

Example:

```http
GET /api/accounts/summary
```

Example response:

```json
{
  "success": true,
  "data": {
    "totalAccounts": 100,
    "totalBalance": "25000.00"
  }
}
```

The example values are illustrative.

### 3.5 Retrieve account details

**Endpoint:** `GET /api/accounts/:id`

Retrieves the details of a specific account.

Example:

```http
GET /api/accounts/ACCOUNT_UUID
```

Replace `ACCOUNT_UUID` with the actual account UUID.

The response contains the account information, including its current balance.

## 4. Transaction APIs

### 4.1 Create a credit transaction

**Endpoint:** `POST /api/accounts/:id/transactions`

Adds money to the selected account and creates a transaction record.

Example:

```http
POST /api/accounts/ACCOUNT_UUID/transactions
```

Request body:

```json
{
  "type": "credit",
  "amount": "500.00",
  "referenceId": "CREDIT-001",
  "description": "Initial deposit"
}
```

The `description` field is optional.

### 4.2 Create a debit transaction

**Endpoint:** `POST /api/accounts/:id/transactions`

Deducts money from the selected account and creates a transaction record.

Request body:

```json
{
  "type": "debit",
  "amount": "100.00",
  "referenceId": "DEBIT-001",
  "description": "Cash withdrawal"
}
```

Validation and business rules:
- The transaction type must be `credit` or `debit`.
- The amount must be greater than zero.
- The amount must have no more than two decimal places.
- The reference ID is required.
- The reference ID must be unique for the account.
- A debit must not exceed the available balance.
- The account must exist.

The balance update and transaction record must be committed together.

### 4.3 Retrieve account transaction history

**Endpoint:** `GET /api/accounts/:id/transactions`

Returns a paginated transaction history for an account.

Example:

```http
GET /api/accounts/ACCOUNT_UUID/transactions?page=1&limit=10
```

Query parameters:

| Parameter | Description | Example |
|---|---|---|
| `page` | Page number | `1` |
| `limit` | Number of records per page | `10` |

The response contains the account's transactions and pagination metadata. Transactions are displayed newest first.

### 4.4 Retrieve transactions across all accounts

**Endpoint:** `GET /api/transactions`

Returns a paginated list of transactions across all accounts.

Example:

```http
GET /api/transactions?page=1&limit=10
```

The response includes transaction details and account information where available, together with pagination metadata.

## 5. Transfer API

### 5.1 Transfer money between accounts

**Endpoint:** `POST /api/transfers`

Transfers money from a source account to a destination account.

Request body:

```json
{
  "sourceAccountId": "SOURCE_ACCOUNT_UUID",
  "destinationAccountId": "DESTINATION_ACCOUNT_UUID",
  "amount": "200.00",
  "referenceId": "TRANSFER-001"
}
```

Replace the example IDs with actual account UUIDs.

Validation and business rules:
- Both accounts must exist.
- Source and destination accounts must be different.
- The amount must be greater than zero.
- The amount must have no more than two decimal places.
- The reference ID is required.
- The source account must have sufficient funds.
- A successful transfer creates a debit transaction for the source and a credit transaction for the destination.
- Both balance changes and both ledger entries must be committed atomically.

If the transfer fails, neither account should have a partial balance update or a partial set of transfer entries.

## 6. Pagination

Account and transaction listing endpoints support pagination through `page` and `limit` query parameters.

Example:

```http
GET /api/transactions?page=2&limit=20
```

Pagination metadata follows this structure:

```json
{
  "page": 2,
  "limit": 20,
  "totalRecords": 100,
  "totalPages": 5
}
```

The values shown are examples.

## 7. Error Handling

The API validates request data and rejects operations that violate business rules.

Common error scenarios include:

| Scenario | Expected behavior |
|---|---|
| Invalid account UUID | Reject the request |
| Account does not exist | Return an account-not-found error |
| Missing account name | Reject account creation |
| Invalid transaction type | Reject the transaction |
| Zero or negative amount | Reject the transaction |
| More than two decimal places | Reject the transaction |
| Duplicate transaction reference | Reject the duplicate |
| Insufficient balance | Reject the debit or transfer |
| Same source and destination account | Reject the transfer |
| Missing required fields | Return a validation error |

Typical HTTP status codes include:
- `200 OK` — Successful retrieval or operation, depending on the implementation.
- `201 Created` — Successful resource creation, if used by the endpoint.
- `400 Bad Request` — Invalid request data.
- `404 Not Found` — Resource does not exist.
- `409 Conflict` — Duplicate reference or conflicting operation, if configured.
- `500 Internal Server Error` — Unexpected server failure.

The exact status code and error response depend on the endpoint implementation and error middleware. Confirm them against the running backend before submission.

## 8. Data Integrity

The application follows these data integrity principles:

- Monetary amounts are stored using PostgreSQL `NUMERIC(19,2)`.
- Decimal.js is used for monetary calculations.
- New accounts begin with a zero balance.
- Transaction records are immutable through the available API.
- Reference uniqueness is enforced according to the account and transfer rules.
- Database transactions protect related balance updates and ledger entries.
- Transfers maintain matching debit and credit entries.
- Failed operations must not modify balances partially.
